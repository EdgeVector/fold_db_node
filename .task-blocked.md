BLOCKED: face-discovery-3node `bob.shared_record_count[Photography] >= 1` cannot pass at the
current fold_db pin (rev `25605233` at the time of writing) because the data-share receive
path does not preserve the original sender's `pub_key` on a HashRange schema's per-key
`AtomEntry`, AND `FieldVariant::resolve_value` does not surface per-key `writer_pubkey`
into `FieldValue.writer_pubkey` for non-Single variants. The assertion is correct; the
upstream plumbing required to satisfy it for HashRange schemas does not exist.

What's needed to unblock
========================

An upstream change in `fold_db` (and a follow-up rev bump on this repo) along these lines:

1. `fetch_atoms_with_key_metadata_async_with_org` (`crates/core/src/schema/types/field/filter_utils.rs`)
   currently hardcodes `writer_pubkey: None` when assembling `FieldValue`s. It needs the
   per-key `AtomEntry.writer_pubkey` looked up from the molecule for that variant — Hash,
   Range, and HashRange — and stamped onto each returned `FieldValue`. (Single already gets
   it via `FieldVariant::molecule_writer_pubkey()`.)

2. The data-share receive path (`fold_db_node::handlers::discovery::inbound::process_data_share`)
   constructs `Mutation::new(..., payload.sender_public_key, MutationType::Create)` and then
   calls `db.mutation_manager().write_mutations_batch_async(...)`. Inside fold_db, the
   per-key signing layer (`MoleculeHashRange::set_atom_uuid_from_values`,
   `MoleculeHash::set_atom_uuid`, `MoleculeRange::set_atom_uuid`) signs the `AtomEntry`
   with the **local node's** `signer` keypair (`self.signer` on `MutationManager`), so
   `AtomEntry.writer_pubkey` ends up as the local node's pubkey, NOT
   `mutation.pub_key`. fold_db needs either:
     a. A "replay/import" code path that lets the caller stamp a non-local `writer_pubkey`
        + `provenance` directly onto the AtomEntry without re-signing locally, OR
     b. `MutationManager` to honor `mutation.pub_key` / `mutation.provenance` when set
        (e.g. `Provenance::User { pubkey, signature }`) and propagate it onto the
        AtomEntry instead of always overwriting via the local signer.

   Without (2), fix (1) alone would surface the **local node's** pubkey as `author_pub_key`
   for shared records — still wrong for the assertion (which expects Alice's pubkey).

Until both land, the test framework has no observable signal for "this record was authored
by another node" on a HashRange schema.

Why a stop-gap pin-back is NOT viable
=====================================

The bug entered when `fold_db` PR #544 ("feat: add Ed25519 signatures to molecule writes",
merged 2026-04-15) renamed `source_pub_key` → `writer_pubkey` and removed
`source_pub_key` from `Atom` (it had been populated per-atom in the pre-#544 path). After
#544, `writer_pubkey` only flows for Single molecules; per-entry writer_pubkey on
HashRange/Hash/Range AtomEntries never reaches the query response.

Pinning fold_db back to pre-#544 (parent of `3b81e3fd`) is not feasible because every
fold_db PR since then is a load-bearing dependency of fold_db_node:

- #545 Cross-User Sharing Extension
- #564 org dual-read fallback for pre-tag molecules (alpha BLOCKER 3e063)
- #615 Provenance::User wire-through
- #617 DerivedMetadata plumbing for view compute-as-mutations
- #629 fold_db → Cargo workspace conversion (structural)
- #641 log → tracing migration (Phase 3)
- #681/#683/#684 schema utoipa derives (required by `src/openapi.rs` registration)
- #685 drop FOLD_STORAGE_PATH (paired with fold_db_node `30be0b8` / PR #829)

Pinning back would break openapi.rs registration (#683 dependency) and reintroduce
FOLD_STORAGE_PATH on the consumer side (PR #829 already deleted it here). So the
defensive-pin-back path is closed.

Why the schedule has been silently masked since 04-25
=====================================================

Every nightly between 04-25 and 05-03 either failed at build (cancelled / GitHub-runner
churn) or failed at `alice_ingest` before reaching the assertion. The 05-04 run is the
first scheduled run since PR #408 added the assertion (2026-04-13) where every upstream
step succeeded — and that's what surfaced this dormant bug. The PR #408 description's
"Verified against dev cloud" note was from an interactive run on 04-13, when fold_db
was still pre-#544 (rev a0434b2539... shipped pre-#544's plumbing change). So the test
verified once on the working code path, then the path was removed by the upstream
rename, and CI never observed the regression until 05-04.

Recommended next step
=====================

File this as an upstream issue / PR against `fold_db` covering BOTH plumbing gaps:
preserving the original sender's pubkey through `process_data_share` ingestion AND
surfacing per-AtomEntry `writer_pubkey` to FieldValue/FieldMetadata for HashRange
schemas. The assertion in `test-framework/scenarios/face-discovery-3node.yaml:91` and the
test helper `get_shared_record_count` (`test-framework/lib/assertions.sh:79-102`) can
stay exactly as they are — they're correctly shaped for a post-fix world.

Once the fold_db fix lands and the bump-cascade bot picks it up here, this branch can
be closed without any fold_db_node code change.
